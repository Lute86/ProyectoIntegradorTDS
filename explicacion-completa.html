Explicacion Completa del Proyecto

Proyecto Integrador TDS — IFTS 29 — GoSoftware — Junio 2026

Que construimos

Desarrollamos una plataforma web dinamica para el IFTS N°29 que reemplaza su antiguo sitio WordPress. El sistema tiene dos caras:

  • Sitio publico: un sitio web moderno y responsivo donde aspirantes, estudiantes y el publico en general pueden consultar la oferta academica, noticias, eventos, horarios, y contactar al instituto.
  • Panel de administracion: un back office donde el personal del instituto (administradores, profesores, tutores) gestiona todo el contenido sin saber programacion: noticias, carreras, materias, horarios, eventos, galeria de imagenes, testimonios, usuarios, y hasta la personalizacion visual del sitio.

El sistema es 100% funcional con backend en Express + Sequelize, frontend en React 19 + Vite + TailwindCSS 4, todo orquestado con Docker. Tiene 86 archivos de test (214 solo en frontend), autenticacion JWT con roles, y personalizacion visual en vivo.

Actores del sistema: Administradores (control total), Profesores (gestionan contenido academico), Tutores (acceso de lectura + novedades), Estudiantes (portal con horarios), Publico general (consulta informacion).

Arquitectura general

Browser → Vite (dev) / Nginx (prod) → Frontend React 19 ↔ API REST ↔ Backend Express 5 → Sequelize ORM → SQLite (dev) / PostgreSQL (prod)

El frontend es una SPA (Single Page Application) que se comunica con el backend via HTTP (Axios). React Router 7 maneja la navegacion del lado del cliente. Zustand 5 gestiona el estado global. Los formularios usan React Hook Form + Zod para validacion.

El backend sigue un patron de modulo consistente para cada entidad: Modelo (Sequelize) → Migracion → Servicio (logica de negocio con manejo de errores) → Controlador (recibe request, responde JSON) → Validator (express-validator) → Rutas. Hay 15 modulos backend implementados.

Todos los servicios estan envueltos en handleDbErrors que traduce errores de Sequelize (UniqueConstraint, ValidationError, ForeignKeyConstraint) a AppError con codigos HTTP apropiados (400, 404, 409). Los controladores usan asyncHandler para evitar try/catch repetitivos.

Backend en profundidad

Patron de modulo backend

Cada entidad del backend sigue 6 archivos en App/backend/src/modules/{modulo}/:

  1. Modelo (models/X.model.js) — Define esquema Sequelize con tipos, validaciones, relaciones.
  2. Migracion (migrations/YYYYMMDDHHMMSS-create-X.js) — Schema SQL ejecutable via make migrate-dev.
  3. Servicio (services/X.services.js) — Logica de negocio envuelta en handleDbErrors que traduce errores Sequelize a AppError.
  4. Controlador (controllers/X.controller.js) — Recibe req/res, valida input, delega al servicio, responde JSON via helpers tipados (success, created, deleted, etc.). Envuelto en asyncHandler.
  5. Validador (validators/X.validator.js) — Cadenas de express-validator (check body, query, params).
  6. Rutas (routes/X.routes.js) — Define endpoints con stack de middlewares: auth → rol → validacion → controlador.

Middleware pipeline completo

Request → helmet() → compression() → morgan() → cors() → rate-limit → express.json() → static /uploads → health /api/health → routes /api/* → 404 handler → global errorHandler
  1. helmet() — Headers de seguridad (X-Frame-Options, CSP, etc.).
  2. compression() — Gzip en respuestas JSON.
  3. morgan() — Logging HTTP (combined en prod, dev en dev).
  4. cors() — { origin: FRONTEND_URL, credentials: true }. En dev acepta localhost:5173.
  5. rate-limit — 100 requests/minuto en /api/*. El login tiene su propio limitador (10 cada 15 min).
  6. express.json() — Parsea body JSON.
  7. Static /uploads — Sirve archivos subidos (imagenes de galeria).
  8. Health check — GET /api/health devuelve { status: 'ok', db: 'sqlite'|'postgres', env: 'dev'|'prod' }.
  9. Routes — 14 prefijos montados en /api/.
  10. 404 handler — notFound(res, 'Ruta no encontrada').
  11. Global errorHandler — Captura errores, loguea con Winston, responde JSON.

Flujo de autenticacion backend

  1. POST /api/auth/login con { email, password }.
  2. Middleware loginLimiter (express-rate-limit: 10 intentos/15min).
  3. Middleware loginValidation (express-validator: email valido + password not empty).
  4. authController.login recibe request, corre validationResult(req). Si hay errores, responde 400.
  5. Llama a authService.login(email, password) envuelto en handleDbErrors.
  6. Dentro del servicio:
    • User.findOne({ where: { email } }) — si no existe, lanza UnauthorizedError('Usuario no encontrado').
    • user.activo === false — lanza ForbiddenError('Usuario inactivo').
    • bcrypt.compare(password, user.password_hash) — si falla, lanza UnauthorizedError('Contrasena incorrecta').
    • Payload JWT: { id, email, rol }. Firma con jwt.sign(), expiresIn: '8h' (default).
    • Actualiza user.ultimo_acceso.
    • Retorna { token, user: { id, nombre, apellido, email, rol } }.
  7. Controlador responde con success(res, result, 'Login exitoso').

Middleware authenticate

App/backend/src/middlewares/auth.middleware.js

  • Extrae header Authorization: Bearer {token}.
  • Si falta o no es Bearer → 401 "Token no proporcionado".
  • jwt.verify(token, JWT_SECRET) — si falla: JsonWebTokenError → 401 "Token invalido", TokenExpiredError → 401 "Token expirado".
  • Busca User.findByPk(decoded.id) — si no existe o no activo → 401 "Usuario no valido o inactivo".
  • Setea req.user = { id, nombre, apellido, email, rol, avatar_url } y llama next().

Fallo seguro: Si JWT_SECRET no esta definido en entorno, el modulo lanza error fatal al importarse.

Middleware authorize

App/backend/src/middlewares/role.middleware.js

authorize('admin', 'profesor') devuelve un middleware que verifica req.user.rol contra la lista. Si no coincide, responde 403 "Acceso denegado. Rol insuficiente."

Flujo de datos tipico

  1. El usuario completa un formulario en un modal admin.
  2. React Hook Form + Zod validan los datos del lado del cliente.
  3. Si pasa validacion, el modal llama a una accion del store de Zustand.
  4. El store llama al servicio Axios correspondiente.
  5. Axios envia la peticion al backend (el interceptor agrega el token JWT).
  6. Express ejecuta middlewares: autenticacion (JWT) → roles (RBAC) → validacion (express-validator).
  7. El controlador recibe la request y delega al servicio.
  8. El servicio ejecuta la logica de negocio, envuelto en handleDbErrors.
  9. Sequelize ejecuta la consulta en SQLite/PostgreSQL.
  10. La respuesta viaja de vuelta: modelo → servicio → controlador → JSON → Axios → store → componente React.

Componente ProtectedRoute: Tiene dos modos de uso:

  • Modo layout: Sin children, renderiza AdminLayout con un <Outlet> para rutas hijas.
  • Modo guard: Con children, verifica autenticacion y roles. Si el usuario no tiene el rol necesario, muestra ForbiddenPage.

Props que recibe: user (objeto o null), loading (boolean), allowedRoles (array de strings opcional), children (ReactNode opcional).

Logica interna completa:

  1. Si loading === true — renderiza null (espera a que AuthContext termine de hydratar).
  2. Si !user — redirige a /login via <Navigate to="/login" replace />.
  3. Si allowedRoles existe y user.rol no esta incluido:
    • Si hay children → renderiza <ForbiddenPage />.
    • Si no hay children → redirige a /admin/dashboard.
  4. Si paso todas las validaciones → renderiza children (modo guard) o <AdminLayout /> (modo layout).

ForbiddenPage: Pagina simple con icono de candado, texto "Acceso denegado", descripcion "No tienes permisos para acceder a esta seccion" y boton "Volver al inicio".

FE1 — Sistema de autenticacion

AuthContext.jsx

App/frontend/src/contexts/AuthContext/AuthContext.jsx

Es el mecanismo principal de autenticacion. Se consume via el hook useAuth() que devuelve { user, loading, login, logout }.

Maquina de estados del login:

  • Estado inicial: { user: null, loading: true } — verificando sesion previa.
  • Hydration: al montar el provider, lee localStorage.getItem('token') y localStorage.getItem('user'). Si ambos existen, parsea user (JSON) y setea estado. Si no, loading = false.
  • Login exitoso: { user: {...}, loading: false }.
  • Login fallido: { user: null, loading: false }, muestra error.

Metodos:

  • login(email, password):
    1. setLoading(true).
    2. POST /api/auth/login con { email, password } via Axios.
    3. Si la API responde ok, extrae { token, user } de response.data.data (doble anidamiento: response.data.success.data).
    4. Guarda en localStorage: 'token' (string) y 'user' (JSON.stringify).
    5. Setea estado { user, loading: false }.
    6. Si la API falla (error) Y las credenciales son admin@ifts29.edu.ar / admin1234:
      • Crea objeto mockUser = { nombre: 'Admin', apellido: 'IFTS 29', email, rol: 'admin', avatar_url: null }.
      • Guarda mock en localStorage.
      • Setea estado con el mock.
      • Nota: Esto es un fallback de desarrollo para cuando el backend no responde. En produccion, el backend siempre debe estar disponible.
    7. Si no son las credenciales mock: setea mensaje de error "Credenciales invalidas" y loading = false.
    8. Edge case: login() no tiene wrap try/catch dentro del store (CRIT-07) — si Axios lanza error de red, la promesa se rechaza sin manejo.
  • logout(): Elimina 'token' y 'user' de localStorage, resetea user a null.

App/frontend/src/pages/admin/LoginPage/LoginPage.jsx

api.js — Cliente Axios centralizado

App/frontend/src/services/api.js

Todas las llamadas HTTP pasan por esta instancia de Axios (baseURL: '/api', Vite lo proxy al backend):

Request interceptor:

  1. Lee token: localStorage.getItem('token').
  2. Si existe: config.headers.Authorization = 'Bearer ' + token.
  3. Si config.data instanceof FormData: elimina config.headers['Content-Type'] para que el browser autosetee el boundary multipart con multipart/form-data.
  4. Devuelve config modificado.

Response interceptor (error handler):

  1. Si error.response.status === 401:
    • Verifica que window.location.pathname !== '/login' (evita bucle si el error ocurre en login).
    • Elimina 'token' y 'user' de localStorage.
    • Redirige a /login via window.location.href = '/login'.
  2. Para otros codigos: rechaza la promesa con Promise.reject(error) para que cada store lo maneje individualmente.

Edge case: Si el token expira mientras el usuario esta en una pagina admin, la siguiente llamada al backend recibe 401 y el usuario es redirigido automaticamente al login. No hay refresh token implementado — el usuario debe volver a autenticarse.

StatItem.jsx

App/frontend/src/components/public/Stats/StatItem.jsx

Componente que muestra un contador animado con requestAnimationFrame:

Funcion parseValor(valor):

  • Usa regex para descomponer strings como "+1500 estudiantes" → { prefix: "+", num: 1500, suffix: " estudiantes" }.
  • "95%" → { prefix: "", num: 95, suffix: "%" }.
  • "3" → { prefix: "", num: 3, suffix: "" }.

Funcion de easing easeOutCubic: t => 1 - Math.pow(1 - t, 3). Proporciona aceleracion negativa: empieza rapido, frena al final.

Bucle de animacion animateValue:

  1. Registra startTime = performance.now().
  2. En cada frame: calcula elapsed = now - startTime, progress = Math.min(elapsed / 1500, 1).
  3. Aplica easing: easedProgress = easeOutCubic(progress).
  4. Calcula valor actual: currentDisplay = Math.round(easedProgress * targetNum).
  5. Construye string: displayValue = prefix + currentDisplay + suffix.
  6. Si progress < 1, pide el siguiente frame via requestAnimationFrame(step).

Condiciones de arranque:

  • La animacion solo comienza cuando isVisible === true (desde useScrollReveal).
  • Si el numero objetivo es 0, renderiza "0" sin animacion.
  • Si el valor no se puede parsear (NaN), muestra el string original directamente.

FE7 — Dark mode

El dark mode se implementa mediante una combinacion de tecnologias:

  1. ThemeContext: Provee { theme, toggleTheme, setTheme }. Almacena en uiStore que persiste en localStorage. Togglea la clase .dark en <html>. Escucha prefers-color-scheme para auto-deteccion.
  2. TailwindCSS dark: prefix: Todos los componentes usan dark:bg-slate-800, dark:text-white, etc. El @variant dark en globals.css activa estos estilos cuando el ancestro tiene clase .dark.
  3. Transicion global: El * { transition: ... } en globals.css hace que el cambio entre light y dark mode sea suave (0.3s).
  4. Navbar toggle: Boton sol/luna en el navbar publico y en MobileMenu.

FE6 — Consultas admin

ConsultasPage.tsx (admin)

App/frontend/src/pages/admin/ConsultasPage/ConsultasPage.tsx

Pagina admin para gestionar consultas del formulario de contacto publico:

Estado local:

  • isModalOpen (boolean) — controla visibilidad del modal de detalle.
  • consultaActiva (Consulta | null) — consulta seleccionada para ver/respuesta.
  • searchTerm (string) — filtro de busqueda en nombre, email o asunto.

Store (consultasStore.ts):

  • Estado: consultas[], unreadCount, isLoading, error.
  • Metodos: fetchConsultas() (GET /consultas), fetchUnreadCount() (GET /consultas/unread/count), responderConsulta(id, respuesta) (PUT /consultas/{id} con { respuesta, respondido: true }), eliminarConsulta(id) (DELETE /consultas/{id}).

Tabla: Columnas Nombre, Email (hidden lg:table-cell), Asunto, Fecha (hidden md:table-cell), Estado (badge verde "Respondida" / ambar "Pendiente" segun c.respondido). Acciones por fila: "Ver Detalle" (azul), "Finalizar" (verde, solo si pendiente), "Borrar" (rojo).

ConsultaDetailModal.tsx: Modal de detalle que muestra nombre, email, asunto, fecha, estado, mensaje (con whitespace-pre-wrap) y campo de respuesta (textarea). Boton "Finalizar" llama a responderConsulta() y cierra. Boton "Abrir correo" construye link mailto: con asunto y cuerpo para responder desde el cliente de email.

Topbar integration: AdminTopbar muestra un contador de consultas no leidas (unreadCount) como badge rojo en la campanita de notificaciones.

FE8 — Comisiones N:M + refactor horarios

Modelo de datos

FE8 implementa la relacion triple N:M entre Comisiones, Carreras y Materias:

Comision ──belongsTo──> Carrera (una comision pertenece a una carrera) Comision ──belongsTo──> User (encargado, opcional) Comision ──belongsToMany──> CarreraMateria (via ComisionCarreraMateria) └── through: ComisionCarreraMateria { comision_id, carrera_materia_id } Horario ──belongsTo──> CarreraMateria Horario ──belongsTo──> Comision (como comisionInfo)

comisionesService.js

App/frontend/src/services/comisionesService.js

Wrapper Axios con metodos: getAll(params), getById(id), create(data), update(id, data), delete(id), assignMaterias(id, carreraMateriasIds) (POST /comisiones/{id}/materias), removeMateria(id, carreraMateriaId) (DELETE /comisiones/{id}/materias/{carreraMateriaId}).

Gestion inline (sin pagina propia)

No existe ComisionesPage independiente. La gestion de comisiones se hace inline dentro de CarreraDetailAdmin.jsx (1298 lineas) en la pestana "Horarios por Comision":

  • Estado local: comisiones[], comisionesLoading, comisionFormOpen, comisionFormData (cuatrimestre, letra, encargado_id).
  • Filtros: Select de año (2026-2040) y cuatrimestre.
  • Creacion de comision: Formulario inline con letra (ej: "A"), cuatrimestre, encargado opcional.
  • Modo compartido: Toggle que permite que una comision tenga materias de diferentes cuatrimestres.
  • Asignacion de materias: Buscador de materias con modal que filtra las ya asignadas a la carrera, permitiendo seleccionar cuales se cursan en esa comision.
  • Validacion de horarios: Dia requerido, horario requerido (hora inicio < hora fin), aula requerida (excepto si modalidad virtual), profesor opcional (min 3 chars si se ingresa).
